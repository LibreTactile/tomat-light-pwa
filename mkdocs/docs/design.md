# **TOMAT Light Design Document**  

## **1. Introduction**  
TOMAT Light is a smartphone alternative to the **TOMAT hardware device** (a "remote control" for the internet). It replicates TOMAT's core functionality while eliminating hardware barriers (cost, distribution, maintenance) by leveraging smartphones and web technologies.  

**Key Advantage:**  
- Instant distribution via Progressive Web App (PWA), no app stores required.  

## **2. User Needs**  
### **Core Requirements:**  
1. **Real-time pairing** with the *TOMAT Navigator* Chrome extension.  
2. **Screen-based simulation** of TOMAT's interface:  
   - **Output**: Haptic feedback (vibration matrix).  
   - **Input**: Touchscreen buttons.  
3. **Tactile feedback** emulating physical components:  
   - **Haptic states**:  
     - `INACTIVE`: Gray appearance, no feedback.  
     - `ACTIVE`: Green appearance, continuous vibration.  
     - `PULSATING`: Red appearance, rhythmic pulses.  
4. **Screen-reader compatibility** for accessibility.  

## **3. System Overview**  

### **Architecture:**  
The system follows a **peer-to-peer architecture** where:
- **PWA** acts as the "Interface" role
- **Chrome Extension** acts as the "Navigator" role  
- **Firebase Firestore** serves strictly as a signaling broker (not a data relay)

Once the WebRTC connection is established, all communication flows directly between peers without server intermediation.

### **Components:**  
- **TOMAT Light PWA** (smartphone app)
- **TOMAT Navigator** Chrome extension  
- **Firebase Firestore** signaling infrastructure

### **Architecture Decisions:**  
- **PWA**: Simplifies development/distribution vs. native apps.  
- **WebRTC**: Enables peer-to-peer communication with NAT traversal (avoids LAN IP restrictions of WebSockets).  
- **Firestore Signaling**: Handles peer discovery, SDP/ICE exchange, and presence tracking.

## **4. Technical Architecture**

### **4.1 Communication System**

#### **WebRTC Manager**
The central communication hub handling:
- **Role-Based Connection**: PWA assumes `interface` role; extension assumes `navigator` role
- **Deterministic Identity**: Peer IDs generated by hashing Public IP + User Agent (enables identity recovery on page refresh)
- **Local Network Discovery**: Peers discover each other by querying Firestore for opposite role sharing the same Public IP

#### **Connection Flow**
1. **Discovery**: PWA registers as "Available"; Navigator queries for Interface peers on same IP
2. **Signaling**: Peers exchange SDP offers/answers and ICE candidates via Firestore
3. **Direct Connection**: WebRTC Data Channel established for peer-to-peer communication

### **4.2 State Management**

#### **State Hierarchy**
1. **INACTIVE** - Gray, no feedback
2. **ACTIVE** - Green, continuous vibration
3. **PULSATING** - Red, rhythmic vibration

#### **State Updates**
The PWA receives JSON state updates via the WebRTC Data Channel. States can be applied at the row level (affecting all buttons in a row) or to individual buttons.

**JSON Protocol Example:**
```json
{
  "rows": [
    {
      "row": 0,
      "state": "ACTIVE"
    },
    {
      "row": 1,
      "buttons": [
        {"id": 0, "state": "PULSATING"},
        {"id": 1, "state": "ACTIVE"}
      ]
    }
  ]
}
```

### **4.3 Input Handling**

#### **Touch Detection**
To ensure reliable tactile feedback on mobile devices, the system uses **coordinate-based touch tracking** instead of standard hover events (which fail during touch sliding).

**Approach:**
- Global touch event listeners track finger position continuously
- Manual boundary detection determines when touch enters/exits button areas
- State transitions trigger vibration precisely at boundary crossings

**Event Flow:**
- Touch enters button → Send "BxD*" event + Start vibration
- Touch exits button → Send "BxU*" event + Stop vibration

### **4.4 Haptic Feedback**

Uses Web Vibration API (`navigator.vibrate()`):
- **ACTIVE**: Continuous buzz pattern
- **PULSATING**: Rhythmic heartbeat pattern

Vibration triggers are bound to coordinate-based boundary crossings for precise tactile feedback.

### **4.5 Signaling & Discovery**

**Firestore-Based Signaling:**
1. **Registration**: Peers register with IP address and role
2. **Heartbeat**: Regular updates indicate peer availability (60-second timeout)
3. **Handshake**: SDP offers/answers exchanged via Firestore sessions
4. **ICE Candidates**: Managed through Firestore sub-collections

## **5. PWA Modules**

### **Communications Module**
- Manages WebRTC connections and data channels
- **Bidirectional Messaging**: 
  - Receives state updates (JSON) from Navigator
  - Sends button events to Navigator

### **Interface Manager**
- **Vibrator Array**: Applies haptic feedback based on received state
- **Button Grid**: Sends press/release events via coordinate tracking
- **Quit Button**: Exits app and closes connections

## **6. Key Design Features**

- **Identity Persistence**: Deterministic peer IDs prevent duplicate connections on page refresh
- **Mobile Optimization**: Coordinate-based touch tracking ensures precise haptic feedback during gestures
- **Offline Handling**: Automatic peer filtering after heartbeat timeout
- **Reliability**: Extension maintains WebRTC state across UI lifecycle events
